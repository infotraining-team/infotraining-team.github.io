Repozytoria

  • Repozytorium jest używane do utrwalenia stanu agregatu oraz jego pobierania ze źródła danych.

  • Zapewnia separację modelu domeny od modelu danych.

  • Pełni rolę mediatora pomiędzy tymi modelami poprzez użycie fasady, która ukrywa złożoność aspektów związanych z persystencją danych

  • Repozytorium dostarcza funkcjonalności podobnej do kolekcji, która umożliwia dodawanie i usuwanie agregatów. Dodatkowo może jawnie udostępnić funkcjonalność umożliwiającą wykonywanie określonych zapytań (kwerend).

Repozytoria różnią się od tradycyjnych sposobów dostępu do danych:

  1. Ograniczają dostęp do obiektów domenowych pozwalając jedynie na zwracanie i utrwalanie stanu dla obiektów aggregate roots. Są odpowiedzialne za zachowanie wszystkich niezmienników dla zwracanych agregatów.

  2. Izolują użytkownika repozytorium (zwykle warstwę serwisu aplikacji) od szczegółów technologicznych związanych z bazami danych

  3. Definiują granicę oddzielającą model domenowy od modelu danych.

Interfejs repozytorium definiowany jest w przestrzeni nazw modelu domeny. Implementacja jest umieszczona w warstwie i przestrzeni nazw związanej z infrastrukturą.

Interfejs repozytorium¶

Przykładowy interfejs repozytorium:

namespace DomainModel
{
    public interface ICustomerRepository
    {
        Customer FindBy(Guid id);
        void Add(Customer customer);
        void Remove(Customer customer);
    }
}

Przykładowa implementacja repozytorium wykorzystująca NHibernate:

namespace Infrastructure.Persistence
{
    public class CustomerRepository : ICustomerRepository
    {
        private ISession _session;

        public CustomerRepository (ISession session)
        {
            _session = session;
        }

        public IEnumerable<Customer> FindBy(Guid id)
        {
            return _session.Load<Order>(id);
        }

        public void Add(Customer customer)
        {
            _session.Save(customer);
        }

        public void Remove(Customer customer)
        {
            _session.Delete(customer);
        }
    }
}

Repozytoria generyczne¶

Często spotykanym rozwiązaniem jest wykorzystanie generycznego interfejsu repozytorium:

namespace DomainModel
{
    public interface IRepository<TAggregate, TId>
    {
        IEnumerable<TAggregate> FindAllMatching(Expression<Func<T, bool>> query);            
        IEnumerable<TAggregate> FindAllMatching(string query);
        TAggregate FindBy(TId id);
        void Add(TAggregate aggregate);
        void Remove(TAggregate aggregate);
    }
}

Repozytorium definiujące kontrakt w modelu domeny dziedziczy po powyższym interfejsie:

namespace DomainModel
{
    public interface ICustomerRepository : IRepository<Customer, Guid>
    {
    }
}

Problem z tak zdefiniowanym kontraktem jest związany z tym, że dla wszystkich agregatów dostarczają one takiej samej funkcjonalności. Nie zawsze implementacja może taki kontrakt zrealizować - niektóre agregaty mogą być przeznaczone tylko do odczytu (read only), a dla niektórych nie można usuwać obiektów. Dla takich repozytoriów implementacja bardzo często wygląda tak:

namespace Infrastructure.Persistence
{
    public class CustomerRepository : ICustomerRepository
    {
        // ....
        public void Remove(Customer aggregate)
        {
            throw new NotImplementedException(
                "A customer cannot be removed from the collection.");
        }
    }
}

Innym problemem takiego interfejsu repozytorium jest wyciek abstrakcji w metodach FindAllMatching. W rezultacie nie jest możliwe kontrolowanie oraz optymalizacja kwerend.

Lepszy rozwiązaniem jest zastosowanie jawnego interfejsu repozytorium:

namespace DomainModel
{
    public interface ICustomerRepository
    {
        Customer FindBy(Guid id);
        IEnumerable<Customer> FindAllThatAreDeactivated();
        void Add(Customer customer);
    }
}

Miejscem ewentualnego stosowania generycznego repozytorium jest implementacja jawnego interfejsu.

namespace Infrastructure.Persistence
{
    public class CustomerRepository : ICustomerRepository
    {
        private IRepository<Customer, Guid> _customersRepository;
        public Customers(IRepository<Customer, Guid> customersRepository)
        {
        }

        // ....
        public IEnumerable<Customer> FindAllThatAreDeactivated()
        {
            _customersRepository.FindAllMatching(new
            CustomerDeactivatedSpecification());
        }

        public void Add(Customer customer)
        {
            _customersRepository.Add(customer);
        }
    }
}

Rezpozytoria a ORM¶

ORM nie jest repozytorium. Repozytorium to wzorzec projektowy (architectural pattern), ORM natomiast umożliwia reprezentację modelu danych w obiektowy sposób. Implementacja repozytorium może używać frameworku ORM w trakcie mediacji między modelem danych a modelem domeny.

Repozytorium definiuje kontrakt umożliwiający persystencję danych, a nie jest warstwą dostępu do danych.

Zarządzanie transakcjami - Unit of Work¶

Do zarządzania transakcjami należy użyć wzorca Unit of Work. Rolą wzorca Unit of Work jest śledzić wszystkie zmiany w agregatach w trakcie wykonywania zadań biznesowych.

Unit of Work śledzi, które obiekty są usuwane, dodawane lub uaktualniane. Repozytorium jest odpowiedzialne za właściwe utrwalenie danych w ramach transakcji koordynowanej przez Unit of Work.

Repozytoria - Antywzorce¶

  • Ad Hoc Queries - ekspozycja w interfejsie repozytorium metod, które umożliwiają tworzenie kwerend ad hoc

    public interface ICustomerRepository
{
    void Add(Customer customer);
    Customer FindBy(Guid Id);
    IEnumerable<Customer> FindBy(CustomerQuery query);
}
    public interface ICustomerRepository
{
    void Add(Customer customer);
    Customer FindBy(Guid Id);
    IQueryable<Customer> Customers();
}

    • Takie interfejsy osłabiają kontrakt. Repozytorium nie powinno być otwarte na rozszerzanie. Jego zadaniem jest utworzenie granicy między modelem domeny a modelem danych.

  • Lazy Loading - agregaty powinny być tworzone wokół niezmienników i zawierać wszystkie niezbędne właściwości wymagane przez logikę biznesową. Leniwe ładowanie danych umożliwia załadowanie tylko części agregatu. Jeśli takie zachowanie jest akceptowalne, to najprawdopodobniej nieprawidłowo zdefiniowane są granice agregatu.

  • Użycie repozytoriów w raportach - potrzeby interfejsu użytkownika oraz logiki biznesowej są odmienne. Jeśli tylko dwie właściwości są potrzebne do wyświetlenia widoku, z repozytorium ładowany jest cały agregat. Podobnie, jeśli widok potrzebuje informacji z kilku agregatów, muszą one zostać załadowane z repozytoriów. Lepiej w takim przypadku bezpośrednio skorzystać z framework’a dostępu do danych (ORM). Nie należy abstrahować persystencji danych w przypadku pobierania danych dla widoków (raportów).
